Learning project · ray tracing fundamentals

Monte Carlo Path Tracer

A from-scratch, multithreaded C++17 renderer built to learn the fundamentals behind real-time ray tracing — global illumination, physically based materials, and acceleration structures — ahead of applying to AMD's Ray Tracing / Neural Rendering team.

What this is

I wanted to actually understand ray tracing — not just the vocabulary — before applying to a rendering role, so I built a path tracer from first principles: rays, intersection math, Monte Carlo sampling, physically based materials, and a spatial acceleration structure, all measured and benchmarked rather than taken on faith.

Every pixel in the render above is the average of 100 independently sampled light paths, each bouncing up to 12 times through the scene — diffuse, metal, and glass surfaces all obey the same underlying light-transport integral, just with different scattering rules.

Why the BVH matters

Without an acceleration structure, testing a ray against a scene costs O(N) — every object, every ray. A bounding volume hierarchy lets a ray that misses a bounding box skip everything inside it, which is the same underlying idea GPU ray-tracing hardware accelerates in silicon. I measured it directly on this scene's 487 spheres:

Linear scan (no BVH)8.51s
BVH-accelerated1.36s
Same 487-sphere scene, same 300×168 / 32 spp / depth 8 settings — the BVH alone is a 6.24× speedup, and the gap widens as scene complexity grows.

Project architecture

vec3.h3D vector math + Monte Carlo sampling helpers
ray.hParametric ray: origin + t × direction
interval.h / aabb.hRange utility + axis-aligned bounding box (BVH primitive)
hittable.h / sphere.hIntersectable interface + ray–sphere intersection
bvh.hBounding volume hierarchy for O(log N) intersection
material.hLambertian, Metal, and Dielectric BRDFs
camera.hCamera model, Monte Carlo render loop, multithreading
main.cppScene construction, CLI, benchmark mode
